# Risques de migration, priorités et mesures

> Nouvelle decision utilisateur apres M2 : cible a quatre services larges sur une instance/base PostgreSQL, schemas et credentials separes. Prospects et interactions appartiennent a Client & CRM. Le [plan de decomposition courant](coarse-services-plan.md) remplace les anciennes recommandations de ce document ; les preuves historiques M1/M2 restent conservees.


Ces constats décrivent les **risques d'une extraction**, pas une déclaration d'exploitation de vulnérabilités dans le code actuel. Les FK/verrous/transactions existants sont souvent des protections : les supprimer sans équivalent créerait le problème. Aucun service cible ni stratégie de reprise n'a été testé dans cette intervention.

| ID / gravité | Constat vérifié et risque | Mesure et preuve exigées avant bascule |

| R1 — Critique | RevocationRaceTests dépend d'Organization.select_for_update partagé entre révocation et CRM. Remote check/JWT puis commit indépendant crée une fenêtre d'accès après révocation. | Admission/fencing/résolution d'opérations, revalidation après attente et échec fermé ; tests multi-base attente/révocation, crash, expiration, partition et commit tardif. Aucun succès de révocation tant qu'une opération non résolue pourrait contourner sa garantie. Différer la bascule si non démontré. |
| R2 — Critique | client_queryset joint IAM/Party/Prospect ; contrôle uniquement au Gateway ou filtrage après pagination peut révéler clients, finance, prospects et compteurs. | IAM = grants, Client = scope/classification, contrôles dans chaque service ; assertions signées/limitées + fraîcheur, accès directs et headers forgés testés. Comptage/recherche/exports sur même périmètre avant pagination. |
| R3 — Critique | Fichiers/migrations et données existantes à préserver ; route flip après nouveaux commits peut perdre historique et ressusciter anciens droits. | Backup/restore approuvés et prouvés, gel et writer unique, copie/delta inverse vérifiés, aucun vieux snapshot comme rollback automatique. IAM : ne pas restaurer des grants révoqués. Sans procédure sans perte, gel + correction en avant. |
| R4 — Critique | create_prospect compose create_party/sous-type/CRM/qualification/audit dans une transaction. Deux services naïfs laisseraient un prospect orphelin ou visible comme client. | Classification Client autoritaire, préparation cachée, activation après qualification durable, opération idempotente, reprise/crash à chaque étape, aucun delete d'identité/audit comme compensation. |
| R5 — Critique | Publication actuelle snapshot-only ; l'appellation « intégration » ou « reconciliation » pourrait être interprétée comme approbation du mapping. | Garder Carthago read-only, aucun endpoint/credential/schema Carthago inventé ; automatisation acquiert des snapshots seulement. Tests prouvant clients/comptes inchangés ; application de mapping explicitement désactivée sans politique approuvée. |
| R6 — Haute | audit.record utilise la même base/transaction ; HTTP audit après commit peut perdre un événement, audit avant commit mentir sur un succès. | Journal append-only + outbox dans transaction locale, replay/inbox idempotente et alertes. Garder événements historiques intacts. Valider retard du central ; historique d'import local immédiatement disponible. |
| R7 — Haute | FK User/Organization/Membership et SQL composite same-org ne traversent pas des bases indépendantes. Retirer ces FK sans validation affaiblit l'intégrité. | UUID stables, références locales minimales validées par propriétaire, contraintes locales same-org, état/version et non-réaffectation, vérification intégrale avant suppression additive des FK distantes. Pas de cascade réseau. |
| R8 — Haute | Migrations ingestion/clients/audit dépendent d'identity/0002 et AUTH_USER_MODEL ; triggers SQL non décrits entièrement dans models.py. | Préserver anciennes lignées, nouvelles migrations propriétaires, tests bases vides et restore ; contrôler triggers, noms tables, PK et dates. Ne pas installer tout le schéma historique dans chaque service ou utiliser --fake pour masquer une divergence. |
| R9 — Haute | Gateway change l'IP vue par login et les informations TLS/Origin ; settings actuels sans contrat de proxy production. | Source IP issue d'un proxy explicitement autorisé seulement, rejet XFF forgé, limites réelles, Secure/Host/Origin/CSRF et absence de redirect loop testés. Session/secret conservés chez IAM ; pas de clé globale partagée. |
| R10 — Haute | Migration des sessions/password hashes/SECRET_KEY peut déconnecter les utilisateurs ou invalider les budgets HMAC ; copier les sessions dans chaque service multiplie l'autorité. | IAM seul propriétaire, préserver formats/UUID/expiration et secret nécessaire pendant transfert ; tester ancienne session et logout/révocation. Rotation ultérieure contrôlée distincte, aucun secret dans docs/images/logs. |
| R11 — Haute | Import idempotent par clé composite, quotas/verrous org ; nouveaux workers ou retries Gateway pourraient publier/créer deux fois. | Reprendre digest, template_version/date_format/as_of/snapshot_kind/org exactement ; garde locale unique, transactions et double acteur ; pas de retry mutation opaque, commandes internes à clé+digest, tests simultanéité/timeout/rejeu. |
| R12 — Haute | Commandes métier et références sensibles peuvent être mises en cache dans des projections. Retard d'événement de révocation/affectation/classification expose les données. | Projection jamais autorité d'accès ; confirmation de révision/fraîcheur avant utilisation, refus fermé en retard/indisponibilité. Le polling React 30 s n'est pas une mesure serveur. |
| R13 — Haute | UI dépend d'erreurs 403/409, JSON Workspace Zod, chaînes Decimal, pagination et CSV ; OpenAPI partiellement générique. | Tests consommateurs et comparaison direct/Gateway, aucun renommage URL, autorisation/compteurs identiques ; tests uploads/réponses 200/201/204, casts/types ne remplacent pas la validation runtime. |
| R14 — Haute | Copie vers service peut exposer des tables hors domaine et données sensibles aux credentials du candidat. | Bases/roles séparés, copie sélective uniquement après approbation backup/privacy ; permissions minimales migration/runtime, réseau privé et authentification inter-services ; test échec de connexion à la base voisine. |
| R15 — Moyenne | Tests actuels construisent Identity/Client/Audit ensemble et s'importent mutuellement ; suites vertes ne prouvent pas l'indépendance. | Fixtures synthétiques locales, contrats API simulés + tests réels inter-services séparés ; aucune FK/connexion/fixture étrangère nécessaire pour démarrer les tests isolés. Garder tests PostgreSQL, pas seulement SQLite. |
| R16 — Moyenne | Gateway et appels IAM deviennent des points de panne ; un système distribué augmente latence, timeouts et coûts d'exploitation. | Readiness/timeouts bornés, pas de retry aveugle mutation, corrélation et alertes backlog. Échec fermé explicite ; mesures de charge avant caches d'autorisation. Compose/HTTP/outbox suffisent au MVP, sans Kubernetes/Kafka. |
| R17 — Moyenne | Images actuelles runserver/Vite dev, secret d'exécution non séparé du propriétaire de schéma ; trigger append-only ne protège pas d'un DBA/DDL. | Serveurs applicatifs et proxy appropriés au déploiement, rôles runtime sans DDL/TRUNCATE, backups protégés et restauration ; revue d'exploitation dédiée avant production. Ne pas présenter l'audit actuel comme preuve cryptographique. |
| R18 — Moyenne | Appeler les sept conteneurs « services » alors qu'ils partagent tables/déploiement ne corrige pas l'architecture. | Checkpoint explicite de quatre services propriétaires pour le MVP ; Reconciliation/Reporting/AI créés quand métier prêt ; tests de déploiement/migration N/N-1 et panne indépendants. |

## Décisions encore nécessaires

1. Validation sécurité du protocole de révocation/admission et de ses modes de panne ; aucune autorisation donnée pour accepter des droits périmés.
2. Responsable de chaque donnée et validation du retard admissible de consolidation audit ; rétention/accès des journaux et backups.
3. Environnement réel à migrer, fenêtre de maintenance, RPO/RTO, approbation backup et procédure de retour après commits. Cet audit n'infère aucune présence ou autorisation d'accès à une production.
4. Méthode/cadence/credentials read-only Carthago et mapping/propriété approuvés. Leur absence bloque les seules opérations correspondantes, pas le CRM autonome.
5. Formules KPI, matrice production, règles de campagne/agenda et politiques IA, avant les nouveaux services fonctionnels.

## Conditions d'arrêt d'une bascule

Refus différent ou accès élargi ; écriture après révocation ; divergence de PK/version/digest/sous-type/provenance ; audit manquant ou mutable ; deux writers actifs ; permissions DB trop larges ; procédure de restauration non éprouvée ; modification d'un attribut source non approuvée. Dans ces cas, fermer le nouveau chemin d'écriture, préserver les preuves/données et appliquer la procédure de retour testée ou corriger en avant. Ne pas élargir temporairement les rôles pour faire passer la recette.

## Limites de la vérification présente

Analyse source + métadonnées PostgreSQL en lecture seule + checks Django/migrations/OpenAPI. Historique de tests explicitement séparé des tests exécutés dans [current-architecture](current-architecture.md#tests-et-vérifications-de-cet-audit). Pas d'essai de bascule/restauration, de nouvel E2E, de comparaison visuelle ou de test multi-service : aucune architecture cible déclarée opérationnelle.
