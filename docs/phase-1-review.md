# Revue critique Phase 1

Revue du 13 novembre 2026, limitée au code et à l'environnement disponibles. Les sévérités ci-dessous sont des priorités d'ingénierie pour AICED ; elles ne constituent pas une notation CVSS ou une certification de sécurité.

## Constats confirmés et corrections, par gravité

| ID | Gravité | Constat avant correction | Correction et preuve |
|---|---|---|---|
| R1 | Haute | DRF 3.16.1 était couvert par des avis de sécurité sur parsing/charset et négociation Accept. AICED exposait JSONParser et la négociation standard ; les voies AdminRenderer et TokenProxy ne sont pas activées ici. | Mise à jour du verrou et des contraintes vers DRF 3.18.3 ; drf-spectacular 0.30.0 testé avec cette version. Tests d'un charset `bz2_codec` et d'un paramètre Accept excessif : refus sans mutation. Références primaires ci-dessous. |
| R2 | Haute | La limite Django de corps de requête n'était pas appliquée au chemin `request.data` de la version DRF utilisée : un JSON de plus de 256 octets était accepté malgré une limite configurée de 256. | Test échouant avant correction (200 au lieu de 413). Limite de 64 KiB par défaut au niveau Django et parser JSON borné par octets, avec lectures fragmentées couvertes. Le dépassement produit une enveloppe JSON 413. Les médias non JSON sont refusés ; JSON trop imbriqué renvoie 400. Configuration des limites strictement positive. |
| R3 | Haute | Une écriture CRM attendait le verrou client après avoir lu ses grants. Une révocation pouvait commiter pendant cette attente et l'écriture se poursuivait avec une autorité devenue obsolète. | Test concurrent PostgreSQL déterministe reproduisant `updated` au lieu de `denied` avant correction. Le service prend le verrou d'organisation utilisé par les changements de droits puis réévalue les permissions avec une nouvelle requête, avant verrou client et mutation. Le test passe désormais. |
| R4 | Haute | `grants()` se fiait uniquement au `User.is_active` en mémoire. Un acteur désactivé en base pouvait encore appeler un service avec un objet User conservé en mémoire. | Test reproduisant une écriture autorisée après désactivation SQL. Ajout de `membership__user__is_active=True` à la sélection des grants. L'appel de service avec cet acteur obsolète est maintenant refusé. |
| R5 | Moyenne | Le logout écrivait `logout.succeeded` avant la suppression de session. Une panne de suppression laissait une fausse trace de succès. La connexion persistait aussi son état et son audit dans des étapes séparées. | Test de panne de suppression reproduisant le faux succès avant correction. Services transactionnels de session : persistance explicite de connexion et audit atomiques ; suppression de session puis audit de déconnexion atomiques. Test de panne d'audit : aucune session authentifiée ni mise à jour last_login conservée. |
| R6 | Moyenne | Les validations de payload étaient dans les vues uniquement. Le service notes acceptait plus de 5 000 caractères ; `TextField(max_length=...)` ne constituait pas une limite SQL. Les appels directs des autres services ne validaient pas leur contrat complet. | Test échouant avant correction. Validation centralisée dans les services (champs inconnus, scope, booléens, notes). Migration `clients.0004_crmprofile_crm_notes_length` appliquée : même un QuerySet.update trop long est rejeté. Les vues ne répètent plus la validation. |
| R7 | Moyenne | Plusieurs réponses OpenAPI étaient `dict` sans champs, notamment le jeton CSRF. Un schéma valide formellement ne décrivait donc pas le contrat de réponse. | Test échouant sur l'absence de csrfToken dans le schéma. Serializers explicites pour session, CSRF, accès, catalogue de rôles, notes CRM et enveloppe d'erreurs ; UUID explicites pour les liens de Party. OpenAPI valide avec `--fail-on-warn`, sans avertissement. |
| R8 | Moyenne | Un administrateur ne pouvait pas retirer un grant expiré/désactivé ou désactiver un membership dont les seules capacités étaient expirées, car la délégabilité était exigée même pour une autorité non effective. | Retirer une autorité non effective est permis à users.manage dans l'organisation. Aucune réactivation supplémentaire autorisée ; les gardes de délégation/reprise de droits restent en place. Tests de nettoyage de grants et de désactivation passés ; tests de refus de désactivation d'un manager actif toujours passés. |
| R9 | Faible | Les listes d'accès utilisaient values_list malgré un prefetch, la comparaison de délégabilité était répétée pour deux scopes alors que sa politique exige maintenant l'autorité organization dans les deux cas. | Réutilisation des collections préchargées, suppression du paramètre scope devenu inutile et de la comparaison répétée. Aucun cache de permissions persistant ajouté. |

Les tests initiaux reproduisant R2–R7 sont conservés dans la suite ; les sorties avant correction sont locales dans `.local/review-before*.log`. Les autres améliorations disposent de tests de non-régression ou d'une vérification statique explicite. Les autorisations effectives demeurent contrôlées côté serveur, jamais par le frontend seul.

Références primaires pour R1 : [limite de corps JSON](https://github.com/encode/django-rest-framework/security/advisories/GHSA-2m8g-3cmr-wg3w), [codecs du parser](https://github.com/encode/django-rest-framework/security/advisories/GHSA-3547-9m27-7rxg), [négociation Accept](https://github.com/encode/django-rest-framework/security/advisories/GHSA-33wh-fxxf-88vv), [version DRF 3.18.3](https://github.com/encode/django-rest-framework/releases/tag/3.18.3).

## 1. Fonctionnalités vérifiées

- **64 tests réussis sur PostgreSQL 17.11**, aucun ignoré : Django 5.2.19, DRF 3.18.3, drf-spectacular 0.30.0. Inclut isolation entre clients d'une même organisation et entre organisations, finance distincte, refus staff/superuser/Group, délégation, expiration, révocation, CSRF, sessions, input validation et intégrité de l'audit.
- Concurrence PostgreSQL vérifiée pour le budget de connexion et pour l'écriture bloquée pendant une révocation.
- Migrations appliquées, dont la nouvelle contrainte de notes. `check` sans anomalie ; `makemigrations --check --dry-run` sans changement ; génération et validation OpenAPI avec `--fail-on-warn` réussies.
- Test HTTP réel `python scripts/smoke_proxy.py` : Vite relaie vers Django ; santé 200, session anonyme 403, Origin non autorisée 403, connexion synthétique avec cookie et CSRF 200, renouvellement du jeton, liste de clients filtrée, finance refusée, déconnexion 204 puis session refusée. Les deux serveurs temporaires sont arrêtés en fin de test. Aucun dossier client n'est modifié.
- TypeScript et Vite build réussis. Deux avertissements de commentaires d'annotation Zod subsistent, sans erreur de compilation. Aucun écran métier créé.
- Contrôle public des avis de dépendances : après mise à jour, aucun avis retourné par OSV pour les 17 distributions Python runtime interrogées, y compris psycopg-binary ; npm audit complet retourne zéro avis dans l'arbre verrouillé. Ces contrôles reflètent les bases d'avis au moment de la revue et ne prouvent pas l'absence de toute vulnérabilité.

Preuves locales ignorées : `.local/review-tests.log`, `.local/review-schema.yaml`, `.local/review-python-advisories-after.json`, `.local/review-npm-audit-all.json`. Commandes applicatives : `python scripts/backend_check.py test core identity`, `migrate --noinput`, `check`, `makemigrations --check --dry-run`, `spectacular --file .local/review-schema.yaml --validate --fail-on-warn`.

## 3. Risques ou limites restants

| Priorité de préparation | Limite et effet |
|---|---|
| Bloquant avant données réelles | La matrice de rôles de production, le bootstrap opérateur, SSO/MFA selon politique et les règles de conservation doivent être approuvés. Le seed démonstratif ne les remplace pas. |
| Bloquant avant production | Le compte PostgreSQL local est propriétaire et possède CREATEDB pour les tests. Le runtime de production doit être distinct du compte migration, sans DDL/TRUNCATE. Les triggers ne résistent pas à un DBA privilégié. TLS, proxy, sauvegarde/restauration, secrets et déploiement n'ont pas fait l'objet d'une recette de production. |
| Bloquant avant ingestion financière | FinancialAccount reste une projection locale minimale avec un Party, sans cotitulaires/mandats, lot de publication, snapshot complet/partiel ou SourceRecord. L'unicité source/external_id n'est pas une règle de rapprochement prouvée par les exports. Aucun import financier réel ne doit utiliser ce modèle comme schéma final sans compléter ces contrats. |
| Moyenne | Les événements d'authentification globaux sont en base, mais aucun endpoint opérateur global n'est livré. Les modifications directes SQL/ORM des rôles restent des opérations privilégiées hors services applicatifs et requièrent une procédure d'audit opérateur. |
| Moyenne | Limites réseau/connexions, purge des buckets et rétention/volume des audits restent à exploiter. REMOTE_ADDR derrière un proxy partagé peut agréger les utilisateurs dans un même budget IP ; la gestion de l'adresse client nécessite une configuration de proxy explicitement approuvée, sans faire confiance à un X-Forwarded-For arbitraire. |
| Moyenne | Le verrou d'organisation sérialise les mutations pour garantir la révocation. Le débit n'est pas testé en charge. Les notes remplacent le champ courant : pas de verrou de version client ni d'historique des corps de notes. |
| Non vérifiée | Docker/Compose, CI hébergée, TLS réel, migrations sur données réelles et tests navigateur/accessibilité complets ne sont pas exécutés dans cette revue. |

## 4. Fonctionnalités non implémentées et références visuelles

La liste actuelle de `references/` contient toujours les six PDF métier/vision et les trois classeurs. Les 16 PDF de maquettes d'interface et leur ZIP sont absents. `AICED.pdf` est une vision de projet, pas un ensemble de 16 écrans. L'écran technique frontend ne représente pas les pages CRM décrites ; aucune conformité visuelle à ces maquettes ne peut être vérifiée ni revendiquée. Ce manque est documenté, pas remplacé par un thème inventé.

Non implémentés : pages métier frontend et connexion interactive frontend, Client 360 complet (dont lecture des notes CRM), gestion des identités/affectations par écran, commerce, campagnes, agenda, KPI, scoring, imports/staging/publication, rapprochement, compte joint/mandats, intégration Carthago et IA. Aucune nouvelle règle financière ni statistique synthétique présentée comme réelle n'a été ajoutée. Le CRM de Phase 1 est un socle backend vérifié, pas le produit CRM complet ou un déploiement prêt pour production.
